## Exact blocking fact

Hotfix 080 requires the API DTO `Finding` (`crates/plumb-api/src/openapi.rs`, `pub struct Finding`) to gain the required-nullable field `rule_class: Option<FindingRuleClass>`. The U2.6 write allowlist assumes `Finding` is built only by `list_findings` in `crates/plumb-api/src/routes/model.rs`. It is not. The same Rust struct and the same OpenAPI component schema are shared with the intake projection:

- `crates/plumb-api/src/workflow.rs` builds `Finding { id, code, family, severity, status, message, affected_refs, waiver_ref }` with a struct literal inside `intake_view(report: &IntakeReport)` (`validation_findings.push(Finding { ... })`, about line 261). A new struct field makes that literal fail to compile (`missing field rule_class`). `workflow.rs` is not in the U2.6 allowlist.
- `IntakeReportView.validation_findings: Vec<Finding>` (`openapi.rs`) is embedded in the responses of `routes/questions.rs`, `routes/proposals.rs`, `routes/sessions.rs` and `routes/model.rs` (all through `intake_view(...)`). Setting `rule_class` correctly there needs the active profile, but `intake_view` is a pure function of the stored `IntakeReport` with no `ApiState`/profile access. Giving it one changes its signature and its call sites in `questions.rs`, `proposals.rs` and `sessions.rs`, all outside the allowlist.
- After regeneration, the generated TS `components["schemas"]["Finding"]` requires `rule_class`. `ui/src/components/shared.test.tsx` contains a typed `validation_findings` fixture `{ id, code, family, severity, status, message, affected_refs }` without `rule_class`, so `npm run typecheck` would fail. `shared.test.tsx` is not in the allowlist.

### Rejected workarounds

Each of these is rejected; none may be used during implementation:

- **Always `rule_class = null` for intake findings.** Known profile-backed findings would lose authoritative metadata.
- **Deriving `rule_class` from `Finding.code` in the UI or an API caller.** The active `ValidationProfile` is the only authority (exact `RuleMetadata.id` lookup); no code-prefix inference.
- **Deriving `rule_class` from `Finding.family`.** `family` is the validation gate/family (I0, F1–F4), not the rule class.
- **Hand-editing generated JSON/TypeScript** (`api/modeller.openapi.json`, `docs/api.md`, `ui/src/api/schema.d.ts`). This repairs neither the Rust construction in `workflow.rs` nor the shared semantics.
- **Silently creating a separate intake Finding schema during implementation** (splitting or renaming the component used by `IntakeReportView`). That is an API contract decision requiring an explicit hotfix.

## Required human decision or missing input

**Human decision (frozen): Option 1.** Every API Finding has one semantic `rule_class` contract. Both the persisted `/api/findings` Findings and `IntakeReportView.validation_findings` obtain `rule_class` from the active `ValidationProfile`:

```text
Finding.code
-> exact RuleMetadata.id lookup
-> RuleMetadata.rule_class
-> Finding.rule_class
```

- No code-prefix inference and no family-based inference.
- Unknown/custom code: `rule_class = null`.
- The five-value API vocabulary is unchanged: `external_standard`, `external_interop`, `plumb_core`, `profile_policy`, `organization_policy`.

**Approved resolution direction (not yet implemented; to be frozen by Hotfix 081).** Hotfix 081 should keep one `Finding` DTO and make `intake_view` profile-aware, conceptually:

```rust
intake_view(
    report: &IntakeReport,
    profile: &ValidationProfile,
) -> Result<IntakeReportView, ApiError>
```

or an equivalent profile-aware API; Hotfix 081 may freeze the exact signature. Every call site must use the same active profile associated with its `ApiState`.

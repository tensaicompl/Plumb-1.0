## Exact blocking fact

Hotfix 031 defines `PLUMB.F1.REQ.MODALITY_EXPLICIT` lexically (§§89–94, S1.6 step "The eleven rules (Hotfix 031)"):

- the scan covers whole ASCII case-insensitive words `shall`, `should`, `may`, `must`, `can`, `not` and `cannot`;
- `can` is an unsupported reading, inconsistent with every typed v3 `Modality` (§91);
- a requirement with any unsupported reading violates the rule (§94).

The same hotfix requires the real single-source HR baseline to produce `MODALITY_EXPLICIT = PASS` for all 32 Accepted HR requirements (§161, S1.6 step "Registration, guard and tests (Hotfix 031)").

The immutable fixture's HR-010 reads:

```text
A submitted leave request shall require a manager decision before it can become Approved or Rejected.
```

S1.1 types it `Modality::Shall`, correctly, by its first normative token. Under the §§89–94 rule, though, it carries a supported `shall` reading and an unsupported `can` reading (in the subordinate clause "before it can become"). So `MODALITY_EXPLICIT` must fail it, and the HR baseline gives `MODALITY_EXPLICIT = FAIL` with targets exactly `[HR-010]`. Both requirements cannot hold together.

S1.1 has the same split built in: its first-normative-token rule keeps HR-010 as Shall (Hotfix 026 §§35, 136). The F1 rule as specified scans every modal token instead.

## Exact blocking fact

Hotfix 033 requires a successful consolidation path for duplicate domain nodes:

- §171: two active same-type domain nodes with the same domain-origin identity, the same payload and no incident edges or references must produce a `MergeNodes` Proposal with `MaterialDecision` and `HumanDecision`.
- §172: the keep selection of that proposal (Accepted beats Proposed, otherwise the lexicographically smaller ID) must be demonstrated.
- §228: "safe MergeNodes proposal".
- §§116–118: the `MergeNodes` proposal must be dry-run with `apply_patch` before it is returned.

The authoritative patch semantics forbid that for every S2.1 node type. Metamodel §20.4 says:

> **MergeNodes:** only for `Requirement` or `Term` …

plumb-patch implements exactly that. `Working::merge_nodes` returns `PatchError::MergeTypeUnsupported` for any other node type, before the incident-edge and reference checks. So for an Entity, Attribute or DomainRelationship duplicate, the required dry-run always fails with:

```text
MergeNodes does not support Entity nodes
```

No `MergeNodes` proposal for a domain node can ever be returned. Changing this needs a change to `plumb-patch` and to metamodel §20.4 merge semantics. Both are outside the S2.1 allowlist and explicitly forbidden:

- Hotfix 033 §120: "Do NOT weaken MergeNodes".
- the S2.1 prohibition "Do not modify … plumb-psg/plumb-patch semantics; do not weaken MergeNodes".

The S2.1 acceptance line "Safe existing-node consolidation uses canonical MergeNodes only when the generic patch is lossless/applicable" is satisfiable, because the generic patch is never applicable. The mandatory §171/§172 tests are not.

## Required human decision or missing input

Decide how S2.1 consolidation of same-origin domain duplicates is specified, given that `MergeNodes` is restricted to `Requirement` and `Term`. One of these must change by an explicit revision:

- **the S2.1 consolidation expectation:** same-origin domain duplicates are reported as `DomainConflict::DuplicateDomainOrigin` with `DomainMergeDisposition::UnavailablePatchConstraint`. §171/§172 are rewritten to assert that refusal, for example by checking the keep selection on the constructed, non-returned patch, or by dropping that check. Or:
- **the patch-engine contract:** a separate, explicitly scoped task extends metamodel §20.4 and plumb-patch `MergeNodes` to Entity, Attribute and DomainRelationship. That is a change to the frozen merge semantics, outside S2.1. Or:
- **the scope:** domain-node consolidation is removed from S2.1 and deferred to a later task, keeping only deterministic duplicate-origin conflict reporting.

## Resolution

Resolved by human-approved Plan Hotfix 034.

Human decision: preserve the Requirement/Term-only `MergeNodes` contract of metamodel §20.4. plumb-patch and the metamodel are not changed, and the domain `MergeNodes` proposal expectations of Hotfix 033 (§§171–173, §228 and the keep selection) are removed.

S2.1 duplicate handling is detection and reconciliation only. Same-origin Entity, Attribute or DomainRelationship duplicates yield `DuplicateDomainOrigin` with `UnavailablePatchConstraint` ("MergeNodes is restricted to Requirement or Term nodes; domain-node consolidation is unavailable in S2.1.") and no proposal. Dependents of a duplicated Entity are blocked with `EntityDependencyConflicted`. `DomainMergeDisposition::MergeProposed` is removed.

S2.1 returns from `blocked` to `pending`.

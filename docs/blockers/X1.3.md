## Exact blocking fact

Hotfix 059 requires `crates/plumb-intake/src/lib.rs` to register the X1.3 modules and export the X1.3 API:

- revised X1.3 allowlist: `lib.rs`, `index.rs`, `intake.rs`, `report.rs`, `tests/intake.rs`, `docs/plan/EXECUTION-STATE.yaml`;
- §179: "Register `mod intake; mod report;` and export intentional X1.3 public types/functions", including `IntakeReport`.

The accepted X1.2 integration test `crates/plumb-intake/tests/bm25.rs::bm25::source_guards` scans `lib.rs` together with `bm25.rs` and `index.rs`. It asserts that `lib.rs` contains **neither** of these:

- the intake-semantics tokens in its shared list (`IntakeReport`, `requires_reason`, `covered_by`, `novelty`, `ResolutionDecision`, `Jaccard`, `threshold`, …);
- `assert_absent(LIB_SRC, "lib.rs", &["mod intake", "mod report"])`.

The test was written when X1.2 was required to have no intake gate yet. With the required X1.3 `lib.rs` it fails:

```text
thread 'bm25::source_guards' panicked at crates/plumb-intake/tests/bm25.rs:1464:13:
lib.rs must not contain "IntakeReport"
test result: FAILED. 47 passed; 1 failed
```

The required `lib.rs` also contains `mod intake;` and `mod report;`, which the final assertion forbids. `IntakeReport` is the only shared-list token it contains.

Three parts of Hotfix 059 forbid modifying the test:

- §152: "All 48 X1.2 tests must still pass unchanged";
- §159: do not modify `crates/plumb-intake/tests/bm25.rs`;
- §286: STOP if the work requires "editing files outside the revised X1.3 allowlist".

The only way to pass the guard without editing it would be to hide the tokens, for example `#[path = ...]` module renames, glob re-exports or aliased exports. That would circumvent a guard, and it was not done.

## Blocking category

- `BLOCKED-IMPLEMENTATION-CONTRACT`

There are two independent blockers. Hotfix 083 must resolve both before E0.1 resumes.

## Blocker A — root `tests/` is not a Cargo test target

E0.1 freezes the write path `tests/support/hr_fixture.rs` and the command `cargo test --workspace hr_leave_fixture`. E0.2 (which depends on E0.1) freezes `tests/e2e_hr.rs` and `cargo test --test e2e_hr`.

The repository root `Cargo.toml` contains `[workspace]` (with `resolver = "2"` and the `crates/*` members) and no `[package]` section. The root is therefore a virtual workspace: no Rust package owns the root `tests/` directory (which does not exist today).

- `tests/support/hr_fixture.rs` would not be compiled by any workspace member, so `cargo test --workspace hr_leave_fixture` could never run it.
- `tests/e2e_hr.rs` cannot be a root integration-test target, so `cargo test --test e2e_hr` has no package to resolve it in.

The current E0.1/E0.2 path and command contract is non-executable.

**Preferred direction (for Hotfix 083 to decide):** host the tests in an existing workspace member rather than a new package. The preferred host is `crates/plumb-api`. Its `Cargo.toml` already depends directly on the HR pilot's end-to-end surfaces:

- `plumb-core`, `plumb-artifacts`, `plumb-psg`, `plumb-patch`, `plumb-store`, `plumb-validation`;
- `plumb-inference`, `plumb-compiler`, `plumb-import`, `plumb-functional`, `plumb-sim`, `plumb-intake`, `plumb-session`;
- `serde`, `serde_json`, `serde_yaml`.

It also already has integration tests under `crates/plumb-api/tests/`, so no Cargo dependency change should be needed. A layout along these lines would work:

- `crates/plumb-api/tests/support/hr_fixture.rs` — the reusable support module;
- `crates/plumb-api/tests/hr_fixture.rs` — the E0.1 integration-test driver;
- `crates/plumb-api/tests/e2e_hr.rs` — E0.2, reusing the same helper.

This is not implemented here.

## Blocker B — the three HR expert answers cannot be applied by the current S3.3 service

E0.1 required action 3 says the builder must leave the three ambiguity answers unresolved in the pre-answer graph. It must then apply them only by passing each expert answer to the S3.3 answer application service. Each application produces a ResolutionDecision and a SemanticPatch, committed through the F0.8 CAS revision path.

`fixtures/hr-leave/expert-answers.yaml` defines exactly three answers:

| ambiguity | authoritative value |
|---|---|
| `half_day` | `{decimal: '0.5', unit: working_day}` |
| `holiday_inside_period` | `{holiday_consumes_working_day: false, calendar_ref: cal:PL-Office}` |
| `inclusive_end` | `{inclusive_end: true}` |

**The current S3.3 template set is closed.**

`ResolutionTemplate` (`crates/plumb-functional/src/resolution.rs`) has exactly six variants:

1. `DomainRelationshipCardinality`
2. `StateTransitionTrigger`
3. `OperationPerformer`
4. `CalculationCalendar`
5. `PermissionBinding`
6. `InvariantFormula`

`ResolutionTemplate::of(code, kind)` accepts only these exact (Finding code, QuestionKind) pairs and returns `None` for anything else:

| Finding code | QuestionKind |
|---|---|
| `PLUMB.F2.DOMAIN.RELATION_TYPED` | `Cardinality` |
| `PLUMB.F2.STATE.TRANSITION_COMPLETE` | `PickOne` |
| `PLUMB.F2.OPERATION.PERFORMER` | `RoleAssignment` |
| `PLUMB.F2.TIME.CALENDAR_DEFINED` | `Calendar` |
| `RBAC.F2.PERMISSION.CONCRETE` | `Permission` |
| `PLUMB.F2.INVARIANT.EXPRESSIBLE` | `FormulaConfirm` |

There is no generic answer fallback.

**The S3.1 question registry is equally closed.** `QUESTION_TEMPLATES` (`crates/plumb-functional/src/question_templates.rs`) has exactly six templates, `f2.domain.relationship.cardinality.v1`, `f2.state.transition.trigger.v1`, `f2.operation.performer.v1`, `f2.time.calendar.v1`, `f2.permission.concrete.v1` and `f2.invariant.formula.v1`, for the same six families. Every other finding is unmapped. E0.1 cannot create arbitrary Questions and expect `resolve_question(...)` to apply them.

The three authoritative semantics are unsupported:

- **`half_day`** — `half_day_fraction = 0.5 working_day`. No S3.3 template has an answer schema that accepts `{decimal, unit}`, and no resolution mapper turns it into the HR half-day semantic effect. It is not a cardinality, trigger, performer, calendar reference, permission binding or invariant formula.
- **`inclusive_end`** — `inclusive_end = true`. No S3.3 template accepts `inclusive_end`, and no mapper updates the RequestedWorkingDays business-time boundary semantics from it.
- **`holiday_inside_period`** — `holiday_consumes_working_day = false` together with `calendar_ref = cal:PL-Office`.
  - `CalculationCalendar` accepts only `{calendar_ref}`: its persisted answer schema is `single("calendar_ref")` with `additionalProperties: false`, which `resolve_question` validates before anything else. Its effect only sets `Calculation.calendar_ref`.
  - The complete authoritative answer would therefore be rejected unchanged. Dropping `holiday_consumes_working_day` would leave that part ungoverned, so the existing template cannot be claimed to resolve this ambiguity.

**The production API has no alternative answer path.** `POST /api/questions/{id}/answer` (`crates/plumb-api/src/routes/questions.rs`) calls `resolve_question(...)` directly (`crates/plumb-functional/src/resolution.rs`). There is no broader fallback or generic-patch path for unsupported answer families. This is therefore not only an E0.1 helper problem. Without a production answer-contract repair, E0.2 cannot truthfully prove the chain question rounds -> expert answers -> governed ResolutionDecision patches for all three HR ambiguities.

**Where the mismatch comes from.** The inherited v2 plan (`docs/plan/merged-implementation-plan-v2.md`, M7.3) expected broad answer application:

- one Patch per kind: cardinality, state/transition, outcome, actor allowance, unit/precision/rounding, formula, rule cell, calendar, attribute type;
- "applying `expert-answers.yaml` leaves zero blocking findings".

The implemented v3 S3.3 scope was intentionally narrowed to the six concrete families above. The HR fixture kept the broader inherited expectation. Hotfix 083 must reconcile the two contracts explicitly. The v2 expectation must not be treated as already implemented.

### Rejected workarounds

These would make E0.1/E0.2 test the fixture builder instead of the product. None may be used:

- constructing a ResolutionDecision directly inside the fixture helper as a substitute for production answer behavior;
- hand-building a SemanticPatch for `half_day` or `inclusive_end` while claiming it exercised S3.3;
- mutating the post-answer reference graph directly and only adding Decision nodes for appearance;
- dropping unsupported parts of `expert-answers.yaml`, such as `holiday_consumes_working_day`;
- changing the authoritative fixture inputs to fit the current six S3.3 schemas;
- marking the three values resolved only in generated reference YAML without a real governed production answer path.

The authoritative fixture inputs stay unchanged:

- `fixtures/hr-leave/README.md`
- `requirements.md`
- `requirements.docx`
- `fixture-contract.yaml`
- `scenarios.yaml`
- `expert-answers.yaml`
- `stakeholders.yaml`
- `profile.yaml`

The blocker is in the implementation and plan contract, not in these inputs.

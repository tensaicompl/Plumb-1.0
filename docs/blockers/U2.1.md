## Blocking category

- `BLOCKED-SPEC-MISSING`

U2.1 requires pre-commit semantic-diff previews, but the authoritative API/specification pack defines no operation that can supply them. The missing item is specification/contract material, not an implementation choice.

## Exact blocking fact

U2.1 lacks a server-authoritative pre-commit semantic-change preview contract for both of its governed diff-preview workflows:

- **Glossary merge.** The v3 U2.1 task requires "Glossary merge displays resulting semantic diff before commit", with the acceptance "glossary merge requires diff confirmation". This inherits v2 §8 U3 "Glossary [P] list, conflicts with pick/merge".
- **Requirement split.** U2.1 required action 1 inherits v2 §8 U2 "actions reclassify/waive/split (diff preview)/mark-duplicate".

Current runtime and contract facts:

1. **Glossary merge.** `POST /api/glossary/{id}/merge` (`merge_glossary`) takes `If-Match` and `GlossaryMergeRequest { into, reason }` and returns `WriteResult`. The handler (`crates/plumb-api/src/routes/model.rs` `merge_glossary`) builds the server term-merge Proposal with `plumb_functional::vocabulary::propose_term_merge` and then calls `state.write(…, "merge_glossary")`. That is `ApiState::write` (`crates/plumb-api/src/state.rs`), the shared governed write path: X1.3 intake then CAS commit. It commits immediately. There is no pre-commit semantic diff response.
2. **Requirement split.** `POST /api/requirements/{id}/split` (`split_requirement`) takes `If-Match` and `SplitRequest { parts, reason }` and returns `WriteResult`. The handler (`crates/plumb-api/src/routes/requirements.rs` `split_requirement`) calls `propose_requirement_split(…)` and then `state.write(…, "split_requirement")`, committing immediately. There is no pre-commit semantic diff response.
3. **Model diff.** `GET /api/model/diff` (`get_model_diff`) takes optional `from`/`to` **existing revision IDs** (`to` defaults to head, `from` to the parent of `to`) and returns `ModelDiff`. It compares stored revisions, so it cannot describe a candidate that has not been committed. It is the only operation in `api/modeller.openapi.json` that returns `ModelDiff`.
4. **Generic intake.** `POST /api/proposals/intake` (`intake_proposal`) requires the caller to supply the complete typed `Proposal` JSON (`IntakeRequest { kind, payload, evidence }`). The UI is not authorized to construct the semantic Term-merge or Requirement-split Proposal itself. The operation persists a pending proposal and returns `IntakeResponse` / `IntakeReportView`, which does not supply the required semantic element diff.
5. The only `patch_preview` in the contract is `AnswerResponse.patch_preview` (`POST /api/questions/{id}/answer`), which is unrelated to merge or split.

Therefore:

- **Commit then fetch the diff** (direct merge or split followed by `GET /api/model/diff`) violates the required order: request → server semantic diff → display → explicit confirmation → commit.
- **A client-computed diff or client-built Proposal** violates CLAUDE.md "Never invent …" and plan §16. The semantic effects of `propose_term_merge` and `propose_requirement_split` belong to the backend; `DiffViewer` only presents a supplied server diff.
- **Out of reach for U2.1.** Its write allowlist contains only UI feature files, `ui/src/app/router.tsx` and the i18n catalogues. It cannot add or change the required capability in `api/modeller.openapi.json`, `ui/src/api/schema.d.ts` or `crates/plumb-api/*`.

## Resolution

Resolved by human-approved Hotfix 073.

The missing server-authoritative pre-commit semantic-change preview contract is now frozen for both requirement split and glossary merge. U2.1 owns two preview operations:

- `POST /api/requirements/{id}/split/preview`
- `POST /api/glossary/{id}/merge/preview`

The server builds the real domain Proposal and dry-applies it with the existing patch engine. It reports `base_semantic_hash`, `candidate_semantic_hash` and the exact semantic `added`/`removed`/`modified` IDs, runs intake, and persists the exact pending Proposal bound to the baseline RevisionId. Confirmation uses the existing proposal `supersede`/`merge` actions; moved baselines are rejected (`E_PROPOSAL_BASELINE_CHANGED`) and never rebased.

`candidate_semantic_hash` is explicitly the hash of the candidate graph produced by the domain Proposal. It is not a prediction of the final accepted revision hash, because acceptance governance may add a ResolutionDecision.

Hotfix 073 also adds A0.3 as a U2.1 dependency.

U2.1 returns from `blocked` to `pending`.

## Reopened after Hotfix 073

### Blocking category

- `BLOCKED-SPEC-CONFLICT`

### Exact blocking fact

Hotfix 073 freezes the requirement split preview action as `supersede`, confirmed through `POST /api/proposals/{proposal_id}/supersede`. Any other server classification must be an internal error, and the class must never be coerced. The frozen server authorities classify the exact split Proposal as `create`, not `supersede`:

1. `plumb_functional::propose_requirement_split` (`crates/plumb-functional/src/requirements.rs`) builds `Compound { AddNode child Requirement (Accepted) per part, AddEdge decomposes_to parent→child per part, SetStatus parent Accepted→Superseded }`. It contains no `SemanticPatch::Supersede` leaf.
2. A0.3 `crate::workflow::classify` (`crates/plumb-api/src/workflow.rs`) yields `supersede` only for a `SemanticPatch::Supersede` leaf. For this patch the special-class list is empty, and the added Requirement nodes and `decomposes_to` edges make it `ProposalKind::Create`.
3. `ApiState::act_on_proposal` (`crates/plumb-api/src/application.rs`) runs `classify` then `require_kind`. Even if a preview existed, `POST /api/proposals/{id}/supersede` on the split proposal would be 409 `E_PROPOSAL_ACTION_MISMATCH`; only `/create` would be accepted.

Observed during U2.1 execution: the Hotfix 073 split preview, implemented as specified over the shared preview pipeline, returned `500 E_INTERNAL` (`subsystem: preview_action`) for the fixture split of `req:c`. This is exactly the mandated "unexpected classification" outcome. The acceptance "Requirement split … commits that exact Proposal through the existing proposal supersede endpoint" is therefore unsatisfiable.

All three authorities are outside the U2.1 write allowlist (`crates/plumb-functional/*`, `crates/plumb-api/src/application.rs` and `crates/plumb-api/src/routes/proposals.rs` are forbidden; `crates/plumb-api/src/workflow.rs` is not listed). Requiring `create` instead would coerce the frozen class. Changing the patch or the classifier would alter A0.3 or plumb-functional semantics.

The glossary merge preview is not affected: `propose_term_merge` yields a `MergeNodes` leaf, which classifies as `merge`, and its preview and `/api/proposals/{id}/merge` confirmation worked as specified during execution.

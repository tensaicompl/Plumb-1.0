## Exact blocking fact

`POST /api/questions/{id}/answer` (`answer_question`) persists an exact server-generated pending Proposal, but `AnswerResponse` does not expose the `ProposalKind` computed by the authoritative A0.3 classifier.

- The committed contract (`api/modeller.openapi.json`, `ui/src/api/schema.d.ts`) defines `AnswerResponse` with exactly the required fields `version`, `revision`, `semantic_hash`, `events`, `proposal_id`, `intake` and `patch_preview` (`additionalProperties: false`). It has no `action`, `kind`, `proposal_kind` or equivalent server-derived workflow classification.
- The single authoritative classifier is `crate::workflow::classify(graph, proposal) -> ProposalKind` (`crates/plumb-api/src/workflow.rs`). Its closed classes are `link`, `merge`, `supersede`, `create` and `accept`. `ApiState::act_on_proposal` (`crates/plumb-api/src/application.rs`) runs `classify` then `require_kind`, so each of `POST /api/proposals/{id}/link|merge|supersede|create|accept` accepts only the matching class and otherwise returns 409 `E_PROPOSAL_ACTION_MISMATCH`.
- Question-resolution Proposals do not have one fixed class. Existing backend coverage (`crates/plumb-api/tests/http_workflow.rs`, `http_workflow_end_to_end_answer_preview_accept_and_stale_if_match`) proves that a performer answer (`{"performer_ref": "actor:clerk"}`) yields a pending Proposal that adds a semantic `performed_by` relation. It is therefore Create-class: `POST /api/proposals/{proposal_id}/accept` is rejected with 409 `E_PROPOSAL_ACTION_MISMATCH`, and only `POST /api/proposals/{proposal_id}/create` succeeds.

U2.2 requires "Inline answer creates server proposal and shows patch preview before acceptance", and inherited v2 U5 requires "answer → proposal card → confirm". Its UI-only allowlist provides no way to obtain the authoritative action class:

- Deriving `ProposalKind` from `patch_preview` in React would duplicate the frozen server classifier (recursive `Compound` flattening, semantic-hash-contributing node types, semantic relations and special-class ambiguity rules). That is not authorized.
- Offering all proposal actions and letting the user discover the valid one through 409 responses is not the specified flow, which is proposal preview followed by one explicit valid confirmation.

Therefore U2.2 cannot implement a deterministic, valid confirmation path with the current frozen contract.

The U2.2 write allowlist (`ui/src/features/sentences/SentencesPage.tsx`, `ui/src/features/sentences/sentences.test.tsx`, `ui/src/features/questions/QuestionsPage.tsx`, `ui/src/features/questions/questions.test.tsx`, `ui/src/app/router.tsx`, `ui/src/features/home/HomePage.test.tsx`, `ui/src/i18n/en.json`, `ui/src/i18n/pl.json`) contains none of the server/API contract material a repair would touch. That includes `crates/plumb-api/src/openapi.rs`, `crates/plumb-api/src/routes/questions.rs`, `crates/plumb-api/tests/openapi.rs`, `crates/plumb-api/tests/http_workflow.rs`, `api/modeller.openapi.json`, `docs/api.md` and `ui/src/api/schema.d.ts`.

The rest of U2.2 is implementable with the current API and is not part of this blocker:

- sequential sentence bulk acceptance with a fresh If-Match after each commit;
- sentence unknowns with real `question_id` references;
- `GET /api/questions`;
- `TypedAnswerControl` driven by `Question.kind` and `answer_schema`;
- display of the raw server `patch_preview` before confirmation.

## Additional contract ambiguity discovered during preflight

U2.2 required action 4 says "Question round manager never permits more than profile max", but no runtime profile maximum exists for the UI to read:

- Hotfix 046 / S3.2 (`docs/plan/PLUMB-IMPLEMENTATION-PLAN-v3.md`, S3.2 actions 1–2) states that `plumb_validation::ValidationProfile` "stays validation-rule metadata and gains no question_round_size". It defines `QuestionRoundConfig {question_round_size: usize}` as "explicit orchestration input supplied by the caller, valid only for 1..=1000, with no implicit production default". Tests may read `question_round_size: 15` from `fixtures/hr-leave/profile.yaml`; production code never parses it.
- The live API matches this. `CreateRoundRequest {stakeholder, max}` is validated by `round_size(max)` (`crates/plumb-api/src/application.rs`) against `1..=MAX_QUESTION_ROUND_SIZE`, where `MAX_QUESTION_ROUND_SIZE = 1000` (`crates/plumb-functional/src/round.rs`).
- Inherited v2 U5 (`docs/plan/merged-implementation-plan-v2.md` §8 U5) says "analyst round manager (compose ≤ 15, …)".

U2.2 must not choose between 15, 1000 or another configured value. The same human-approved specification repair should state what "profile max" means for the U2.2 round manager.

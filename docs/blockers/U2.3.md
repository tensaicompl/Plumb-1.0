## Exact blocking fact

U2.3 requires a project room plus a scoped session side panel, but no authoritative UI route is defined for the project room, and no deterministic mapping exists from route or view to `CreateSessionRequest.scope`.

- U2.3 required actions: "Implement project/scoped side panel", and (Hotfix 071) "mount the project/scoped session panel" in `ui/src/app/AppShell.tsx` and "register ... any project-room route the frozen behavior requires". The inherited source (`SRCREF-CC24FC894A`, v2 §8 U6) says "side panel on scoped views + project room". Neither names a project-room path or which views are "scoped".
- The frozen navigation (`ui/src/app/nav.ts`, Hotfix 071) contains `/`, `/requirements`, `/model/glossary`, `/model/sentences`, `/model/entities`, `/model/processes`, `/model/scenarios`, `/model/findings`, `/model/rules`, `/model/calculations`, `/questions`, `/decisions` and `/gates`. It has no `/sessions`, `/chat`, `/project-room`, `/project` or equivalent. (`/api/sessions` is an API path, not a UI route specification.)
- The backend accepts only an explicit, caller-supplied scope. `POST /api/sessions` (`create_session`, `crates/plumb-api/src/routes/sessions.rs`) parses `CreateSessionRequest {scope}`; every scope ID must exist (404 otherwise) and be `Accepted` (`ScopeNotAccepted` otherwise). The backend never derives scope from the current route. Architecture §5.4 (`SRCREF-7CA117913F`, X1.4) likewise treats scope nodes as mandatory caller-supplied context.

Each of the following would therefore be a new product decision:

- choosing a project-room path;
- treating `scope = []` as the project room (plausible, and permitted by the API, but not frozen as UI behavior);
- deciding which route resource IDs become scope refs. Examples: `/requirements/$requirementId` → `[$requirementId]`; list views such as `/requirements`, `/model/sentences` and `/questions` → `[]`, the visible records, or no panel;
- falling back when a candidate route resource is not `Accepted`.

The UI must not infer scope from URL prefixes, ID prefixes, page text, visible records or selected rows. U2.3 cannot proceed without a frozen session UI contract.

### Secondary gaps (to resolve in the same specification repair)

1. **Streaming.** Inherited U6 says "stream", but `POST /api/sessions/{id}/turns` (`create_session_turn`) is one ordinary request/response operation. There is no session SSE, WebSocket token stream, chunked output or turn-progress endpoint. `/api/events` carries DesignEvents, not assistant output. U2.3 must not fake streaming (artificial reply splitting, polling nonexistent endpoints, `/api/events` as chat output, timers or client token chunks).
2. **Transcript history and provenance links.** The public session operations are exactly `POST /api/sessions`, `GET /api/sessions/{id}`, `GET /api/sessions/{id}/metrics` and `POST /api/sessions/{id}/turns`.
   - `SessionDetail` has only `id`, `scope` and `assistant_actor_ref`.
   - `SessionTurnResponse` has only the current turn: `version`, `revision`, `semantic_hash`, `events`, `reply`, `proposals` and optional `asked_question`.
   - No transcript or turn-history read exists, so inherited U6 "transcript links from provenance" and durable transcript display after reload cannot be supplied.
   - Keeping a page-local transcript in React state would itself be a specification decision.
3. **Proposal action contract.**
   - `SessionProposalView.kind` is produced by the authoritative classifier (`let kind = classify(&loaded.graph, &card.proposal)?; ... kind: wire(&kind)?`), but OpenAPI and the generated TS type it as a plain `string`, not `ProposalKind`. The UI therefore cannot know it is one of `link`, `merge`, `supersede`, `create` or `accept`.
   - Inherited U6 asks for "proposal cards with intake results and full action set". Under the A0.3 classifier a Proposal has exactly one valid positive action plus reject; any other positive action is 409 `E_PROPOSAL_ACTION_MISMATCH`.
   - A decision is needed: either `SessionProposalView.kind` becomes `ProposalKind`, or the UI gets an explicit closed validation and unknown-kind behavior. Separately, it must be decided whether actionable session-card controls are exactly `[classified kind, reject]`, as Hotfix 076 froze for Question proposals.

### Not blocking (implementable with the current API)

- **Engine questions.** `SessionTurnResponse.asked_question` (`string | null`) is guaranteed by X1.4 to be an exposed existing open Question. The UI can resolve it through `GET /api/questions` and render `TypedAnswerControl` from that Question only. An assistant reply that merely looks like a question, with `asked_question == null`, stays assistant text.
- **Intake display.** `SessionProposalView.intake` is the normal `IntakeReportView`.
- **Metrics header.** `GET /api/sessions/{id}/metrics` returns `turns`, `proposals` and `requires_reason`.
- **Turn submission.** `POST /api/sessions/{id}/turns {text, stage}` requires If-Match and takes the closed `SessionStage` (S0..S12); it works through the generated client and `useVersionedMutation`.
- **Proposal endpoints.** `/api/proposals/{id}/accept|create|link|merge|supersede|reject` all exist.

## Resolution

Resolved by human-approved Hotfix 077, which freezes the U2.3 project-room and scoped-session contract.

- **Project room.** The UI project room is `/sessions` and creates sessions with `scope = []`. It is reached from an AppShell "Project room" launcher; `nav.ts` is unchanged.
- **Scoped side panel.** The only current resource-scoped session side panel is `/requirements/$requirementId`. Its exact requirement ID becomes the sole scope ref only when the authoritative `RequirementDetail.status` is `Accepted`. Otherwise session creation is unavailable and never falls back to project scope. Other current routes are not scoped by U2.3, and no generic route-scope inference is created.
- **Turns and transcript.** U2.3 NOW uses request/pending/final-response chat, not token streaming. Its visible transcript is transient current-component state only; no history/resume or provenance transcript links are fabricated. The session stage is chosen explicitly (S0..S12) with no hidden default. Sessions start only on explicit user action.
- **Proposal cards.** `SessionProposalView.kind` is tightened to `ProposalKind` (no new operation; the count stays 74). Session cards expose exactly the classified positive action plus reject, display the already-computed intake, and never rerun `/api/proposals/intake` from the UI.

U2.3 returns from `blocked` to `pending`.

## Exact blocking fact

F0.1 requires three public core contracts that no authoritative document defines exactly:

1. **`Id` validation grammar is undefined.** F0.1 step 1 requires "Id as a validated String newtype" but no authoritative source states what makes an `Id` valid (allowed characters, required `<prefix>:` structure, case, length). The only type definition found is v2's `pub type Id = String;` (no validation). Concrete forms that must be representable are heterogeneous:
   - `src:<16 hex>`, `evd:<16 hex>`, `fnd:`/`q:`/`prop:`/`dec:`/`ses:<16 hex>` (plan §6.1)
   - `rev:<version>:<16 hex>` (plan §6.1)
   - `req:<source_identifier>` with `[A-Za-z0-9._-]+` (plan §6.1)
   - `req:<namespace>:<key>`, `attr:<entity>:<key>`, `resolution:<ulid>` ("recommended forms", metamodel §3.2)
   - `project:leave-management`, `profile:plumb-software-2026.1` (metamodel §3)
   Any validation predicate chosen from these would be invented.

2. **`Hash` prefix contract conflicts with its typed usages.** F0.1 step 1 says "Hash as a sha256-prefixed String newtype", but plan §6.1 defines three hash formats — `sha256:<64 hex>` (artifact), `psg:sha256:<64 hex>` (semantic), `ev:sha256:<64 hex>` (evidence) — and the authoritative Rust sketches type `semantic_hash`, `evidence_hash` and `base_semantic_hash` as the single type `Hash` (compiler architecture §§4.1-4.5; metamodel §20 `base_semantic_hash: Hash`). A strictly `sha256:`-prefixed `Hash` cannot hold `psg:sha256:` / `ev:sha256:` values; accepting them is not "sha256-prefixed". Whether `Hash` accepts all three forms, or separate types exist, is not decided.

3. **`Clock` timestamp type is undefined.** F0.1 step 2 requires a `Clock` trait with `SystemClock` and `FixedClock`. The inherited v2 sketch fixes the method as `pub trait Clock { fn now(&self)->Timestamp; }` (merged-implementation-plan-v2.md §6), but no source defines `Timestamp` (concrete type, precision, UTC/offset handling). Compiler architecture §4.1 also uses the undefined `Timestamp`; plan §6.1 only requires RFC3339 timestamps inside certain ID inputs.

## Resolution — Plan Hotfix 005

The three missing decisions were resolved by human-approved **Plan Hotfix 005** (commit `71495fc`), which adds plan §6.3 "Exact core primitive contracts" and aligns metamodel §§3.1-3.2, compiler architecture §4.1 and the F0.1 task record:

- (a) `Id` grammar: `^[a-z][a-z0-9_-]*:[A-Za-z0-9._-]+(?::[A-Za-z0-9._-]+)*$`, no trimming/normalization, validated conversions and serde.
- (b) `Hash`: one validated type accepting exactly `sha256:`, `psg:sha256:`, `ev:sha256:` + 64 lowercase hex, with `HashKind` and byte-hashing constructors.
- (c) `Timestamp(time::OffsetDateTime)`: UTC-normalized, RFC 3339 input, nanosecond precision, canonical `Z` form with exactly nine fractional digits; `Clock::now(&self) -> Timestamp`.

F0.1 returned from `blocked` to `pending` per plan §14 "Human-approved unblock procedure".

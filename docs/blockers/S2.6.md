## Exact blocking fact

The human-approved Plan Hotfix 040 brief requires a contradiction to be recorded rather than resolved by choice ("If an authoritative existing source contradicts any frozen Hotfix 040 instruction above, do not silently choose one. Record the exact contradiction and STOP."). Hotfix 040 was therefore **not** committed, and no S2.6 code was written.

**Contradiction: the calendar root symbol.** Hotfix 040 §28 requires the PSG-to-PlumbExpr adapter to bind "a calendar root symbol selected in its explicit scope" as `Ty::Ref(calendar_ref_type)` when `Calculation.calendar_ref = C`. The HR formula `working_days([start_date, end_date], calendar, inclusive_end) * day_fraction` (§74) needs such a symbol (`calendar`). But:

- §19 defines the explicit scope as sorted unique **node IDs** (Entity, Attribute, Calculation, Calendar);
- §§16, 17 and 20 derive root symbols from payload names (`Attribute.name`, `Entity.name`, `Calculation.name`);
- the authoritative metamodel §9.9 `Calendar` (and `plumb_psg::Calendar`) has **no name**, only `time_zone`, `week_pattern`, `region?` and `holiday_source?`;
- §15 forbids "name-search guessing", "fuzzy matching" and "hidden global fallback".

So no frozen rule derives the Symbol through which an expression refers to a selected Calendar. Every option would be an unauthorized choice:

- a reserved root symbol `calendar`;
- a caller-supplied symbol;
- a symbol derived from `region` or the node ID;
- a new grounding field in the inference output.

## Related findings (same root cause; for the same decision)

These are not independently contradictory, but they decide whether the §§16–20 adapter can bind real S2.1 output and should be settled together:

1. **Non-symbol names.** §§16, 17 and 20 bind `Attribute.name`, `Entity.name` and `Calculation.name` as PlumbExpr root Symbols. The S2.4 identifier grammar allows only `[A-Za-z_][A-Za-z0-9_]*`. The metamodel names are free strings: S2.1 derives Entity and Attribute names from Accepted Concept names (e.g. `Start Date`, `Leave Request`), and §7 makes `Calculation.name` an exact trimmed requirement substring (it may contain spaces). Such nodes cannot be root bindings; the brief does not say whether that is an adapter error, an ineligible input, or a skip.
2. **HR expression spellings.** The HR expression spellings (`start_date`, `LeaveRequest.start_date`, `RequestedWorkingDays`, `calendar`) therefore cannot come from S2.1-shaped names. §§74–75 can only be shown with a synthetic scope whose names are already valid symbols, consistent with §73, but the adapter's behavior for real non-symbol names still needs a rule.
3. **Scope of an Accepted Calculation.** §24 qualifies Accepted Calculation nodes but does not say where each node's explicit scope (§19) comes from: its `calculation_origin.input_refs`, a caller-supplied scope, or something else. That matters for Calculations not created by S2.6.

## Required human decision or missing input

Freeze how a calculation expression names its calendar. For example:

- a reserved pilot root symbol `calendar` bound to `Ty::Ref(calendar_ref_type)` whenever `Calculation.calendar_ref` is set; or

## Resolution

Resolved by human-approved Plan Hotfix 040 (reissued; the earlier draft was never committed).

Hotfix 040 reserves the PlumbExpr root symbol `calendar`. `Calculation.calendar_ref` is the sole semantic source of that binding; the Calendar node ID serves as both the calendar Ref type and value identity, so no Calendar name is needed.

Ordinary PSG-to-PlumbExpr input names are represented by explicit `CalculationScopeBinding` objects rather than guessed from payload names. Payload names may be used only by an explicit deterministic convenience helper when they are already valid PlumbExpr Symbols. No snake_case, CamelCase, whitespace stripping or other name transformation is performed.

S2.6-created Calculation origins store the exact used scope bindings so Accepted qualification can reconstruct the same TypeEnv. Accepted Calculations not carrying that S2.6 origin require an explicit caller-supplied scope override.

S2.6 returns from `blocked` to `pending`.
